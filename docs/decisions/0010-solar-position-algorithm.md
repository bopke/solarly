# 0010. Solar position algorithm: NOAA simplified equations, refraction included

Status: accepted

## Context

Issue #2 needed `sunPosition(lat, lon, timestampUtc) -> { altitude, azimuth }`
in `solar-physics/`, targeting ~0.01° accuracy against NOAA's public solar
calculator (https://gml.noaa.gov/grad/solcalc/), with zero dependencies. A
few points weren't fully pinned down by the issue/spec text and needed a
decision:

- **Which NOAA algorithm, specifically.** "NOAA's simplified solar position
  algorithm" refers to the equations behind NOAA's own solar calculator,
  documented at https://gml.noaa.gov/grad/solcalc/solareqns.PDF and
  implemented in the calculator's own `main.js`. This is itself a
  simplification of Jean Meeus's low-precision solar position algorithm
  (~0.01° accuracy over the years ~1800-2200), as opposed to a
  full-precision ephemeris (e.g. VSOP87 or JPL DE), which would be
  overkill for a rooftop-PV generation estimator and would pull in a much
  heavier implementation for no practical accuracy gain at this scale.
- **Whether to include atmospheric refraction correction.** NOAA's
  calculator applies a standard refraction correction to the geometric
  elevation before displaying it, so "matches the NOAA calculator" implies
  matching that corrected value, not the purely geometric one. Refraction
  correction has a real (if small) effect near the horizon, which matters
  for early-morning/late-evening generation estimates.
- **Time handling.** The function takes a single UTC `Date`; NOAA's
  original spreadsheet formula for "true solar time" mixes in a local time
  zone offset that cancels out algebraically when the input time is
  already UTC and the offset is treated as 0. This keeps the function free
  of any time zone data/lookup dependency.

## Decision

- Implemented NOAA's simplified/low-precision solar position equations
  (per `solareqns.PDF`), transcribed term-for-term, in
  `src/solar-physics/sunPosition.ts`. No astronomy library dependency.
- Included NOAA's atmospheric refraction correction in the returned
  `altitude`, so the value matches what NOAA's calculator displays as
  elevation (not the uncorrected geometric elevation). This is the
  standard behavior expected by downstream modules that need "will the
  sun actually be visible/how high does it appear," e.g. clear-sky
  irradiance calculations that key off low-altitude behavior.
- `azimuth` is measured in degrees clockwise from true north, 0-360,
  matching NOAA's convention.
- The function takes a UTC `Date` directly (`timestampUtc`); the caller is
  responsible for any local-time-to-UTC conversion. This keeps
  `solar-physics` free of time zone data, consistent with its "pure
  functions, no dependency on any other module" constraint from the M1
  spec.
- Reference test values were generated by an independent Python
  transcription of the same published NOAA equations (not by calling the
  TypeScript function under test), with coefficients cross-checked against
  NOAA's own `main.js` source. This avoids a test suite that would pass
  even if the TypeScript translation introduced a shared arithmetic bug,
  while still validating against the exact algorithm NOAA's calculator
  uses.

## Consequences

- Accuracy for the 1800-2200 date range is ~0.01° for `altitude`, which
  comfortably covers this tool's use case (near-term generation
  estimates). `azimuth` is typically similarly accurate but degrades to
  ~0.05-0.1° (worst observed: ~0.067° in a 3000-sample validation against
  NREL's SPA) near solar zenith, where the azimuth formula's conditioning
  is inherently worse — this is expected behavior of the algorithm, not
  an implementation bug, but a downstream reader sizing an error budget
  should not assume azimuth is as tight as altitude near zenith. Neither
  figure is suitable for historical/far-future astronomical work, but
  nothing in the M1 spec needs that.
- Near the poles or exactly at solar zenith/nadir, the azimuth formula's
  denominator (`cos(lat) * sin(zenith)`) approaches zero. Naively clamping
  the resulting near-infinite ratio into `[-1, 1]` (as an earlier version
  of this module did) does **not** produce `NaN` — it silently returns a
  plausible-looking but wrong azimuth, e.g. `lat=90` returned
  `azimuth=0` exactly, and `lat=89.9999` returned `azimuth≈179.6`, a
  ~180° discontinuity across 0.0001° of latitude. That failure mode is
  more dangerous than `NaN` for a foundational module, since it doesn't
  visibly propagate.

  NOAA's own calculator source (`main.js:303-322`) explicitly guards this
  case (`if (Math.abs(azDenom) > 0.001) { ...compute... } else { azimuth
= latitude > 0 ? 180 : 0 }`) — this module replicates that guard
  exactly, so it matches NOAA's actual behavior at the poles/zenith
  rather than diverging from it. (An earlier version of this ADR
  incorrectly claimed NOAA's calculator shared this module's original
  unguarded limitation; it does not — NOAA guards it, and so does this
  module now.) `altitude` remains well-defined and accurate in all cases;
  only `azimuth` needs the guard.

- Downstream `solar-physics` functions (clear-sky irradiance, POA
  transposition) can rely on `altitude` already including refraction —
  they should not re-apply their own refraction correction.
